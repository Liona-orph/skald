# The Skald wire protocol

Version `1`. JSON over HTTP/1.1, with long polling instead of streaming. The
rationale is [ADR 0002](adr/0002-http-json-transport.md); this document is the
contract.

Everything here is derived from `pkg/api` (the types and paths) and
`internal/frontend` (the transport behaviour). Where the two could drift, the
constants in `pkg/api` are authoritative — the server, the client and the tests
all reference them.

## Conventions

**Transport.** HTTP/1.1. Every operation is a `POST` with a JSON request body
and a JSON response body. `DescribeWorkflow` additionally accepts `GET` with
query parameters. Any other method on a routed path returns `405` with an
`Allow` header.

**Content type.** Requests should send `Content-Type: application/json`.
Responses are `Content-Type: application/json; charset=utf-8` with a trailing
newline.

**Encoding of Go types.** The server marshals Go values with `encoding/json` and
HTML escaping disabled. That fixes three representations you must match:

| Go type | JSON | Example |
| --- | --- | --- |
| `time.Duration` | integer **nanoseconds** | `30000000000` is 30s |
| `time.Time` | RFC 3339 with nanoseconds, UTC | `"2026-05-04T09:12:33.123456789Z"` |
| `[]byte` (`Payload.Data`) | base64 (standard, padded) | `"eyJpZCI6IjEyMzQifQ=="` |

Enumerations are strings, not numbers: `"RUNNING"`, `"ActivityTaskScheduled"`,
`"StartTimer"`, `"HEARTBEAT"`, `"NonDeterminism"`.

**Strict decoding.** Request bodies are decoded with `DisallowUnknownFields`. A
client that sends `retry_polciy` gets `400 invalid_argument` naming the field,
rather than a workflow that silently has no retry policy. More than one JSON
document in the body is also rejected. An **empty** body is accepted and means
"every field at its zero value" — the service layer then produces a better
message than the transport could.

**Body size.** Request bodies are capped at 8 MiB by default
(`--max-request-bytes`). Exceeding it returns `413` with code
`invalid_argument` and a `limit_bytes` detail. Note that this is deliberately
larger than the 2 MiB payload cap, because one request may carry a batch of
commands each with its own payload.

**Compression.** If the request sends `Accept-Encoding: gzip`, responses larger
than 1 KiB (`--gzip-threshold`) are gzipped at `BestSpeed`. Smaller responses
are sent uncompressed — a gzip header and trailer cost more than they save
below that size. `Vary: Accept-Encoding` is set on every response either way.
`gzip;q=0` is honoured as a refusal.

**Operations with no return value** respond `200` with `{}`. The empty object
rather than an empty body lets one client decode path serve every endpoint and
leaves room to add fields without a break.

## Authentication

If `skaldd` is started with an auth token (`--auth-token` / `SKALD_AUTH_TOKEN`),
every route except `/health` and `/ready` requires:

```
Authorization: Bearer <token>
```

`/metrics` **is** protected. Comparison is constant-time. A missing or wrong
token returns `401 unauthorized` with `WWW-Authenticate: Bearer realm="skald"`.

The token is a shared secret, not an identity: it answers "may you talk to this
server" and nothing else. There is no per-caller identity, no per-namespace
access control, and the server has no TLS listener — terminate TLS at a proxy.
The default bind address is `127.0.0.1:7233` for that reason.

## Headers

| Header | Direction | Meaning |
| --- | --- | --- |
| `X-Request-Id` | request and response | Correlation ID. Supplied by the client or generated by the server, and always echoed. Truncated to 128 bytes and stripped of control characters before it reaches a log line. **This is not an idempotency key.** |
| `Skald-Protocol-Version` | request and response | `1`. Absent on a request means "unversioned client" and is accepted. A version the server does not implement is refused with `400 invalid_argument` and a `requested`/`supported` detail. |
| `Retry-After` | response | Delta-seconds, minimum 1. Sent **only** on `429` and `503`. Deliberately absent on `404` and `409`, where retrying the identical request cannot start working. |
| `WWW-Authenticate` | response | `Bearer realm="skald"` on `401`. |
| `Allow` | response | On `405`. |
| `Vary` | response | Always includes `Accept-Encoding`. |

## Errors

Every non-2xx response body is an `api.Error`:

```json
{
  "code": "resource_exhausted",
  "message": "backlog is full",
  "details": { "task_queue": "orders" },
  "retry_after": 2000000000
}
```

- `code` is stable and machine-readable. **Branch on this**, not on the HTTP
  status: the code is carried in the body precisely so that a proxy which
  rewrites statuses cannot lie.
- `message` is human-readable and safe to log. Never parse it.
- `details` is optional structured context.
- `retry_after` is a duration in nanoseconds, mirroring the header.

### Code to status mapping

| Code | HTTP | When |
| --- | --- | --- |
| `invalid_argument` | 400 | Malformed body, unknown field, bad identifier, unknown reuse policy, unsupported protocol version |
| `unauthorized` | 401 | Missing or wrong bearer token |
| `not_found` | 404 | No such execution, run, or endpoint |
| `already_exists` | 409 | The ID reuse policy forbids a second run |
| `version_conflict` | 409 | Lost the optimistic-concurrency race `MaxWriteAttempts` times |
| `failed_precondition` | 412 | The request was well formed and the state machine refuses it: signalling a closed workflow, responding to a task you no longer hold |
| `resource_exhausted` | 429 | Matching backlog full |
| `deadline_exceeded` | 504 | The request's own deadline elapsed |
| `unavailable` | 503 | Store or matcher shut down, or the caller's context was cancelled |
| `internal` | 500 | A bug, an invalid history, or an unrecognised code |

Two mappings are worth defending, and both are deliberate:

- **`version_conflict` and `already_exists` share 409.** They are the same class
  of thing — the request lost a race against current state — and the body
  distinguishes them for anyone who needs it.
- **`failed_precondition` is 412, not 400.** `400` says "your request is
  malformed", which is wrong and misleading: signalling a completed workflow is a
  perfectly well-formed request that the state machine refuses. `412` says "the
  request was fine, the resource was not in the required state", and it keeps
  `400` meaning "fix your client".

Two statuses come from the transport rather than from a code:

- **413** for an oversized body, carrying code `invalid_argument`.
- **405** for the wrong method, carrying code `invalid_argument` and an `allow`
  detail.

An unrecognised code maps to **500**, not 400: the engine inventing a code this
build does not know is a server bug, and blaming the client sends the operator
looking in the wrong process.

### Retry guidance

Retry `unavailable`, `deadline_exceeded` and `resource_exhausted`, with
exponential backoff and jitter, honouring `Retry-After` when present. Never
retry `invalid_argument`, `not_found`, `already_exists` or
`failed_precondition`. `version_conflict` is retryable in principle but is
already retried five times inside the server; a client that sees it is
contending with something pathological.

`pkg/client` implements all of this, including a separate, longer deadline for
long-polling calls so that the general request timeout cannot kill a poll that
is behaving correctly.

## Long polls

Three endpoints can block:

| Endpoint | Blocks |
| --- | --- |
| `/api/v1/tasks/workflow/poll` | Always |
| `/api/v1/tasks/activity/poll` | Always |
| `/api/v1/workflows/history` | Only when `wait_for_new` is true |

Three independent limits end a poll: the client's own context, the server's cap
(`--max-poll`, 50s by default), and the start of a graceful shutdown.

**Fifty seconds is not arbitrary.** The idle timeouts a request crosses on the
way in are typically 60s — the default for an AWS ALB, for nginx's
`proxy_read_timeout`, for Envoy's route timeout and for most ingress
controllers. A poll that outlives one of those is killed *in transit*, and the
worker cannot distinguish that from a task it accepted and dropped. So the
server must give up first, by enough of a margin that clock skew and a slow
response write cannot close the gap. The server refuses to start if the poll cap
is not below the connection idle timeout.

**An expired poll is a success, not an error.** An idle worker is the normal
state of a healthy deployment; a `504` every fifty seconds would produce an
error log per idle minute.

- Task polls return `200` with `{"empty": true}`.
- A history poll returns `200` with the caller's cursor echoed in
  `next_event_id`, so the next poll resumes exactly where this one started.

Poll again immediately. There is no penalty and no backoff expected.

## Idempotency and request IDs

There are two distinct identifiers and they do different jobs.

**`X-Request-Id` (header)** is correlation only. It appears in server logs and
is echoed to the client. It has no effect on behaviour. `pkg/client` generates
one per logical call and **reuses it across retries**, so a log search returns
every attempt of one request rather than fragments.

**`request_id` (body field)** is the idempotency key, and it is honoured on
exactly one operation:

| Field | Honoured? | Effect |
| --- | --- | --- |
| `StartWorkflowRequest.request_id` | **Yes** | A second start with the same `(namespace, workflow_id, request_id)` returns the original run instead of an error. `started` is `false`. Enforced by a partial unique index in the store, so it is safe to retry a start blindly. |
| `SignalWithStartRequest.start.request_id` | **Yes** | Same mechanism. |
| `PollWorkflowTaskRequest.request_id` | **Yes** | Pins the started task to this poll, so a retried poll gets the same task instead of stranding it. |
| `PollActivityTaskRequest.request_id` | **Yes** | Same, for activity attempts. A duplicate `ActivityTaskStarted` for the same request ID returns the existing event rather than an error. |
| `SignalWorkflowRequest.request_id` | **No** | Accepted and **ignored**. `pkg/client` fills it in, and the engine does not read it. Signals are therefore *not* deduplicated: a retried signal delivers twice. Design your signal handlers to tolerate that, or carry your own dedup key in the payload. |

Beyond request IDs, the following are naturally idempotent and safe to retry:

- `CancelWorkflow` — a repeated cancel produces no events and skips the store
  round trip entirely.
- `TerminateWorkflow` on an already-closed run — returns `412`, which tells you
  it was already done.
- `RecordActivityHeartbeat` — moves a deadline; a repeat that moves nothing
  writes nothing.

**Workflow IDs are the real idempotency mechanism for business operations.**
`request_id` makes one API call safe to retry; a workflow ID of `order-1234`
with `id_reuse_policy: "RejectDuplicate"` makes the whole *business operation*
happen at most once, forever.

## Client operations

### `POST /api/v1/workflows/start`

Starts a new execution.

Request — `api.StartWorkflowRequest`:

```json
{
  "namespace": "default",
  "workflow_id": "order-1234",
  "workflow_type": "FulfilOrder",
  "task_queue": "orders",
  "input": { "encoding": "json/plain", "data": "eyJpZCI6IjEyMzQifQ==" },
  "execution_timeout": 86400000000000,
  "run_timeout": 3600000000000,
  "task_timeout": 10000000000,
  "retry_policy": {
    "initial_interval": 1000000000,
    "backoff_coefficient": 2,
    "maximum_interval": 100000000000
  },
  "cron_schedule": "",
  "request_id": "0e0d4f1a-…",
  "id_reuse_policy": "AllowDuplicate",
  "memo": { "team": "billing" },
  "search_attributes": {},
  "identity": "svc@host"
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `namespace` | no | Defaults to the server's `--namespace`. Must match `^[a-zA-Z0-9][a-zA-Z0-9._-]*$`, at most 64 bytes |
| `workflow_id` | **yes** | At most 512 bytes, no control characters |
| `workflow_type` | **yes** | At most 256 bytes, no control characters. The name the worker registered |
| `task_queue` | **yes** | At most 256 bytes |
| `input` | no | A `Payload`. Absent means the workflow observes its zero-valued arguments |
| `execution_timeout` | no | Bounds the logical workflow across retries and continue-as-new |
| `run_timeout` | no | Bounds this run |
| `task_timeout` | no | Bounds how long a worker may hold one workflow task. Defaults to 10s |
| `retry_policy` | no | Workflow-level retry. Normalised server-side; zero fields become defaults |
| `cron_schedule` | no | **Stored and never acted on.** No cron parser exists |
| `request_id` | no | Idempotency key, see above |
| `id_reuse_policy` | no | See below |
| `memo`, `search_attributes` | no | `map[string]string`, stored and returned, **not queryable** |
| `identity` | no | Recorded in event 1 |

`id_reuse_policy` values, matched case-insensitively after stripping `_` and `-`
(so `AllowDuplicate`, `allow_duplicate` and `ALLOW-DUPLICATE` are the same):

| Value | Meaning |
| --- | --- |
| `AllowDuplicate` (default) | A new run is permitted once the previous one closed, in any state |
| `AllowDuplicateFailedOnly` | Permitted only if the previous run did not complete successfully. This is what makes a workflow ID an idempotency key for a business operation |
| `RejectDuplicate` | Exactly one run per workflow ID, ever |
| `TerminateIfRunning` | Terminates any open run, writing a `WorkflowExecutionTerminated` event that explains why, then starts fresh |

An unknown value is **rejected**, not defaulted: silently downgrading
`RejectDuplicate` because of a typo would let a workflow run twice.

Response — `api.StartWorkflowResponse`:

```json
{ "run_id": "0f2e6b78-…", "started": true }
```

`started` is `false` when an existing run was returned because of request-ID
deduplication or reuse policy, which lets a caller distinguish "I started it"
from "it was already running" without a second query.

Errors: `400` invalid identifier or retry policy; `409 already_exists` if the
reuse policy forbids it.

### `POST /api/v1/workflows/signal`

Delivers an asynchronous message to a running workflow.

```json
{
  "namespace": "default",
  "workflow_id": "order-1234",
  "run_id": "",
  "signal_name": "approve",
  "input": { "encoding": "json/plain", "data": "eyJieSI6ImFubmEifQ==" },
  "identity": "svc@host",
  "request_id": "ignored"
}
```

An empty `run_id` means "whichever run is current". `signal_name` is required.
Response: `{}`.

Signals are durable on arrival: a signal the server accepted will be delivered
even if every worker is down. If a workflow task is already in flight, the event
is appended immediately and becomes visible to workflow code on the *next* task.

Errors: `412 failed_precondition` if the workflow is closed; `404` if it does
not exist.

### `POST /api/v1/workflows/signal-with-start`

Signals a running workflow, starting it first if it is not running. It exists
because doing it client-side as "query, then start or signal" has a race that
duplicates work.

```json
{
  "start": { "...": "a full StartWorkflowRequest" },
  "signal_name": "approve",
  "signal_input": { "encoding": "json/plain", "data": "…" }
}
```

Response is a `StartWorkflowResponse`. When it starts, the start event, the
signal event and the first workflow task are all written in **one** store
transaction. When another writer wins the create race, the signal is honoured
against the winner's run and `started` is `false`.

### `POST /api/v1/workflows/cancel`

Requests cancellation. Cooperative: the workflow observes the request on its
next task and decides how to unwind. A workflow that ignores it keeps running,
which is a feature — a payment that must not be abandoned halfway is allowed to
say so.

```json
{ "namespace": "default", "workflow_id": "order-1234", "run_id": "", "reason": "customer withdrew", "identity": "ops@laptop" }
```

Response `{}`. A repeated cancel is a no-op. `412` if already closed.

### `POST /api/v1/workflows/terminate`

Ends the execution immediately. **No workflow code runs**, so nothing the
workflow was holding is cleaned up. That is the difference from cancel.

```json
{ "namespace": "default", "workflow_id": "order-1234", "run_id": "", "reason": "duplicate order", "details": null, "identity": "ops@laptop" }
```

Response `{}`. `412` if already closed.

### `GET|POST /api/v1/workflows/describe`

```
GET /api/v1/workflows/describe?namespace=default&workflow_id=order-1234&run_id=
```

or a `POST` body of `{"namespace": "...", "workflow_id": "...", "run_id": "..."}`.

Response — `api.DescribeWorkflowResponse`:

```json
{
  "namespace": "default",
  "workflow_id": "order-1234",
  "run_id": "0f2e…",
  "workflow_type": "FulfilOrder",
  "task_queue": "orders",
  "status": "RUNNING",
  "started_at": "2026-05-04T09:12:33.123456789Z",
  "closed_at": "2026-05-04T09:13:33.123456789Z",
  "history_length": 7,
  "first_execution_run_id": "0f2e…",
  "pending_activities": [
    {
      "activity_id": "act_1",
      "activity_type": "ChargeCard",
      "scheduled_event_id": 5,
      "attempt": 2,
      "started": true,
      "scheduled_at": "2026-05-04T09:12:33.123456789Z"
    }
  ],
  "pending_timers": [
    { "timer_id": "timer_1", "started_event_id": 6, "fire_at": "2026-05-04T09:13:33.123456789Z" }
  ],
  "memo": {},
  "search_attributes": {}
}
```

`closed_at` is omitted while the run is open. `pending_activities[].started`
means *a worker is holding this attempt right now* — an activity between
attempts reports `false` with an `attempt` above 1. `attempt` here is the live
attempt number, which is not visible in the history (see
[ARCHITECTURE.md](ARCHITECTURE.md#known-limitations-and-what-it-would-take-to-fix-them)).

Describe rebuilds state from history, so it is more expensive than `list`.

### `POST /api/v1/workflows/history`

Reads a run's history, optionally waiting for more.

```json
{
  "namespace": "default",
  "workflow_id": "order-1234",
  "run_id": "",
  "from_event_id": 1,
  "max_events": 100,
  "wait_for_new": false
}
```

- `from_event_id` is **inclusive and 1-based**. Zero or absent means 1.
- `max_events` truncates the returned slice; `next_event_id` reflects the
  truncation, so paging is `from_event_id = next_event_id` in a loop.
- `wait_for_new` turns the call into a long poll that returns as soon as an
  event beyond `from_event_id` exists.

Response:

```json
{
  "events": [ { "id": 5, "time": "…", "type": "ActivityTaskScheduled", "attrs": { "…": "…" } } ],
  "status": "RUNNING",
  "next_event_id": 6
}
```

Stop paging when `next_event_id` does not advance. A terminal `status` with no
further events means the run is complete.

An expired long poll returns `200` with `"events": null` and `next_event_id`
echoing the caller's cursor. Note that `status` in that specific response is the
zero value `"RUNNING"` rather than a fresh read — a poll only reaches the expiry
path for an open execution, so it is accurate in practice, but do not treat it
as a status refresh.

### `POST /api/v1/workflows/list`

```json
{
  "namespace": "default",
  "workflow_id": "",
  "workflow_type": "FulfilOrder",
  "status": "RUNNING",
  "page_size": 100,
  "page_token": ""
}
```

All filters are **exact match**; there is no query language. `status` must be
one of the exact strings in the [status table](#workflow-status). `page_size` is
clamped by the driver (SQLite: default 100, maximum 1000).

```json
{
  "executions": [ { "…": "the same shape as DescribeWorkflowResponse" } ],
  "next_page_token": "…"
}
```

Listing reads visibility rows only. `pending_activities` and `pending_timers`
are **always absent**, and `history_length` is the stored last event ID rather
than a rebuilt count — filling them in would turn one page query into N history
reads. Pagination is keyset-based; pass `next_page_token` back verbatim and stop
when it is empty.

## Worker operations

These are the endpoints a worker SDK implements. `pkg/worker` uses them through
`api.Service`, so a worker can be pointed at an in-process engine instead
without changing anything.

### `POST /api/v1/tasks/workflow/poll`

Long poll for workflow work.

```json
{ "namespace": "default", "task_queue": "orders", "identity": "host@1234", "request_id": "…" }
```

Response — `api.WorkflowTask`. Either an empty task:

```json
{ "empty": true, "execution": { "workflow_id": "", "run_id": "" } }
```

(the zero-valued `execution` is an artefact of Go's JSON encoding; ignore it
when `empty` is true) or real work:

```json
{
  "namespace": "default",
  "execution": { "workflow_id": "order-1234", "run_id": "0f2e…" },
  "workflow_type": "FulfilOrder",
  "task_queue": "orders",
  "scheduled_event_id": 2,
  "started_event_id": 3,
  "attempt": 1,
  "history": [ "… every event from 1 through started_event_id …" ]
}
```

**The full history is always sent.** Skald never sends a delta: sticky caching
is an optimisation the SDK layers on top, and correctness must not depend on a
cache being warm.

The task's deadline is the run's `task_timeout` (10s by default) measured from
`started_event_id`'s timestamp. Respond before it expires or the server times
the task out and schedules a replacement.

### `POST /api/v1/tasks/workflow/completed`

```json
{
  "namespace": "default",
  "execution": { "workflow_id": "order-1234", "run_id": "0f2e…" },
  "commands": [
    { "type": "ScheduleActivityTask", "schedule_activity": { "activity_id": "act_1", "activity_type": "ChargeCard", "input": { "…": "…" }, "start_to_close_timeout": 30000000000 } },
    { "type": "StartTimer", "start_timer": { "timer_id": "timer_1", "start_to_fire_timeout": 90000000000 } }
  ],
  "identity": "host@1234",
  "sdk_name": "skald-go",
  "sdk_version": "0.1.0"
}
```

Command types and their payload fields:

| `type` | Field | Required members |
| --- | --- | --- |
| `ScheduleActivityTask` | `schedule_activity` | `activity_id`, `activity_type`, and at least one of `schedule_to_close_timeout` / `start_to_close_timeout` |
| `RequestCancelActivityTask` | `request_cancel_activity` | `scheduled_event_id` > 0 |
| `StartTimer` | `start_timer` | `timer_id`, non-negative `start_to_fire_timeout` |
| `CancelTimer` | `cancel_timer` | `started_event_id` > 0 |
| `RecordMarker` | `record_marker` | `marker_name` |
| `CompleteWorkflowExecution` | `complete_workflow` | — |
| `FailWorkflowExecution` | `fail_workflow` | `failure` |
| `CancelWorkflowExecution` | `cancel_workflow` | — |
| `ContinueAsNewWorkflow` | `continue_as_new` | — |

Batch rules, all enforced before any event is written so the batch applies
completely or not at all:

- Exactly one populated attribute set per command, matching its `type`.
- At most one **closing** command (`Complete`, `Fail`, `Cancel`,
  `ContinueAsNew`), and it must be last.
- No duplicate activity or timer IDs, within the batch or against currently
  pending ones.
- A cancel must name something pending.
- An activity's heartbeat timeout must not exceed its start-to-close timeout.

Response `{}`. Errors: `412 failed_precondition` if you no longer hold the task
(it timed out, was replaced, or the execution closed) — drop the commands and
replay. `412` also covers a command batch the state machine rejects.

### `POST /api/v1/tasks/workflow/failed`

```json
{
  "namespace": "default",
  "execution": { "workflow_id": "order-1234", "run_id": "0f2e…" },
  "cause": "NonDeterminism",
  "failure": { "type": "NonDeterminismError", "message": "…", "non_retryable": true },
  "identity": "host@1234"
}
```

`cause` is one of `Unspecified`, `NonDeterminism`, `WorkflowPanic`,
`UnhandledCommand`, `UnregisteredType`, `BadCommandAttributes`,
`ResourceExhausted`.

The task is **rescheduled**, not abandoned, whatever the cause. The execution
does not fail. See [ADR 0008](adr/0008-refuse-to-advance-on-non-determinism.md).
Back off briefly before your next poll — the engine reschedules immediately.

### `POST /api/v1/tasks/activity/poll`

```json
{ "namespace": "default", "task_queue": "orders", "identity": "host@1234", "request_id": "…" }
```

Response — `api.ActivityTask`, either `{"empty": true, …}` or:

```json
{
  "namespace": "default",
  "execution": { "workflow_id": "order-1234", "run_id": "0f2e…" },
  "activity_id": "act_1",
  "activity_type": "ChargeCard",
  "scheduled_event_id": 5,
  "started_event_id": 6,
  "attempt": 2,
  "input": { "encoding": "json/plain", "data": "…" },
  "scheduled_at": "2026-05-04T09:12:33Z",
  "started_at": "2026-05-04T09:12:40Z",
  "deadline": "2026-05-04T09:13:10Z",
  "heartbeat_timeout": 10000000000,
  "last_failure": { "type": "Timeout", "message": "…" },
  "last_heartbeat_details": { "encoding": "json/plain", "data": "…" },
  "workflow_type": "FulfilOrder"
}
```

- `deadline` is the instant the server will consider this attempt timed out.
  Derive your context deadline from it, so a doomed attempt stops burning
  resources instead of racing a timeout it cannot win.
- `attempt` is the live attempt number, and `started_event_id` is the *first*
  attempt's event — retries reuse it and write no new event.
- `last_failure` and `last_heartbeat_details` come from the previous attempt,
  which is how a long import resumes at row 40,000 instead of starting over.

### `POST /api/v1/tasks/activity/completed`

```json
{
  "namespace": "default",
  "execution": { "workflow_id": "order-1234", "run_id": "0f2e…" },
  "scheduled_event_id": 5,
  "result": { "encoding": "json/plain", "data": "…" },
  "identity": "host@1234"
}
```

Response `{}`. `404` if the activity is no longer pending; `412` if no worker
currently holds the attempt (it was timed out or retried out from under you).

### `POST /api/v1/tasks/activity/failed`

Same shape with `failure` (required, an `ApplicationError`) instead of `result`.

Whether this is terminal is the server's decision: it consults the retry policy
and, if another attempt is allowed, writes **no history event** at all — the
activity stays pending with a higher attempt counter and a backoff timer. The
workflow sees nothing.

### `POST /api/v1/tasks/activity/canceled`

Same shape with optional `details`. Reports that the activity honoured a
cancellation request.

### `POST /api/v1/tasks/activity/heartbeat`

```json
{
  "namespace": "default",
  "execution": { "workflow_id": "order-1234", "run_id": "0f2e…" },
  "scheduled_event_id": 5,
  "details": { "encoding": "json/plain", "data": "…" },
  "identity": "host@1234"
}
```

Response:

```json
{ "cancel_requested": true }
```

Two things happen at once. The heartbeat deadline is extended, and the response
tells you whether the workflow has asked the activity to stop. **An activity
that never heartbeats can never be cancelled** — there is no other channel
through which the news could reach it.

Heartbeats write no history event, but they do write to the store (a timer-index
row), because the deadline they extend must survive a restart. Throttle client
side; `pkg/worker` throttles to roughly half the heartbeat timeout.

## Operational endpoints

| Path | Method | Auth | Purpose |
| --- | --- | --- | --- |
| `/health` | GET | public | Liveness |
| `/ready` | GET | public | Readiness |
| `/metrics` | GET | **protected** | Prometheus exposition |

`/health` touches nothing and returns `{"status":"ok"}`. Liveness exists so a
supervisor can decide whether *restarting the process* would help, and the
honest answer to "the database is unreachable" is no. A draining server still
reports live: it is running correctly and has simply been asked to stop.

`/ready` performs a one-row visibility query against the store — the same
connection pool, query path and schema real traffic uses — and fails as soon as
shutdown begins. It returns `503` with an `unavailable` body when draining, when
no readiness check is configured, or when the store check fails. The underlying
store error is logged, never returned, because a readiness body is scraped by
infrastructure that is frequently less trusted than the log.

**Pointing a liveness probe at `/ready` is the single most effective way to turn
a brief database blip into a cluster-wide restart storm.** Use `/health` for
liveness and `/ready` for routing.

Any unrouted path returns `404` in the protocol's envelope, so a client only
ever has to parse one shape.

## Shared types

### Payload

```json
{
  "encoding": "json/plain",
  "metadata": { "optional": "string map" },
  "data": "base64 of the encoded bytes"
}
```

`encoding` is `json/plain` for the built-in codec and `binary/null` for the
absence of a value — which is how "no argument" is distinguished from "the JSON
literal `null`". The engine never inspects `data`; keeping the encoding out of
band means a deployment can switch codecs without a history migration, because
old events keep declaring their original encoding.

A single payload is capped at **2 MiB**. Pass a reference (an object storage
key) for anything larger.

### RetryPolicy

```json
{
  "initial_interval": 1000000000,
  "backoff_coefficient": 2,
  "maximum_interval": 100000000000,
  "maximum_attempts": 0,
  "non_retryable_error_types": ["InsufficientFunds"]
}
```

Normalised server-side: a zero `initial_interval` becomes 1s, a zero
`backoff_coefficient` becomes 2, and a zero `maximum_interval` becomes
`min(100 × initial_interval, 100s)`. `maximum_attempts: 0` means unlimited,
bounded only by the schedule-to-close timeout. A `backoff_coefficient` below 1
or a `maximum_interval` below `initial_interval` is rejected.

Backoff is `initial × coefficient^(attempt-1)`, clamped, then spread by up to
20% **upward only** — the stated interval remains a lower bound. The jitter draw
is recorded in history ([ADR 0007](adr/0007-record-retry-jitter-in-history.md)).

### ApplicationError

```json
{
  "type": "InsufficientFunds",
  "message": "balance too low",
  "non_retryable": true,
  "details": { "encoding": "json/plain", "data": "…" },
  "cause": { "message": "…" },
  "stack_trace": "…"
}
```

`type` is the field a retry policy matches on, which is why it is a plain string
rather than a Go type: the workflow inspecting a failure may be written in a
different language than the activity that produced it. `cause` is preserved
across one hop.

### Event

```json
{
  "id": 5,
  "time": "2026-05-04T09:12:33.123456789Z",
  "type": "ActivityTaskScheduled",
  "attrs": { "…": "type-specific" }
}
```

`id` is dense and 1-based. `time` is the server's wall clock at append. A
decoder that encounters an unknown `type` must **fail**, not skip: silently
ignoring an event produces a state that disagrees with the writer's.

Event types, by block:

| Codes | Types |
| --- | --- |
| 1–19 | `WorkflowExecutionStarted`, `Completed`, `Failed`, `TimedOut`, `Canceled`, `Terminated`, `ContinuedAsNew`, `CancelRequested`, `Signaled` |
| 20–29 | `WorkflowTaskScheduled`, `Started`, `Completed`, `Failed`, `TimedOut` |
| 40–59 | `ActivityTaskScheduled`, `Started`, `Completed`, `Failed`, `TimedOut`, `CancelRequested`, `Canceled` |
| 60–69 | `TimerStarted`, `TimerFired`, `TimerCanceled` |
| 80–89 | `MarkerRecorded` |
| 100–119 | **Reserved for child workflows.** Unassigned; a history using them is rejected precisely rather than misparsed |

### Workflow status

`RUNNING`, `COMPLETED`, `FAILED`, `CANCELED`, `TERMINATED`, `TIMED_OUT`,
`CONTINUED_AS_NEW`. Everything except `RUNNING` is terminal.

### Timeout kind

`UNSPECIFIED`, `SCHEDULE_TO_START`, `START_TO_CLOSE`, `SCHEDULE_TO_CLOSE`,
`HEARTBEAT`. For a *run* timeout, `START_TO_CLOSE` means the run deadline and
`SCHEDULE_TO_CLOSE` means the execution deadline across every run.

### Retry state

`Unspecified`, `InProgress`, `NonRetryableFailure`, `Timeout`,
`MaximumAttemptsReached`, `RetryPolicyNotSet`, `Canceled`. This is the field to
read first during an incident: it distinguishes "we gave up" from "we were told
to stop".

## Versioning policy

**The protocol version is `1`**, sent in `Skald-Protocol-Version`. The server
accepts a request without the header and rejects a version it does not
implement, so an old client fails loudly rather than subtly.

Within version 1, these changes are **compatible** and may happen in any
release:

- Adding a new optional request field, or a new response field.
- Adding a new error `code`, or new keys in `details`.
- Adding a new endpoint.
- Adding a new event type in an unused code range, or a new field to an existing
  attribute struct.
- Adding a new command type.

These changes are **breaking** and require a version bump:

- Removing or renaming any field, endpoint, code or enum value.
- Changing the type or meaning of an existing field.
- Changing a status mapping.
- Reusing an event type code for a different meaning.

Two client-side consequences follow, and both bite in practice:

- **Ignore unknown response fields.** The server may add them.
- **The server rejects unknown request fields.** This is asymmetric on purpose:
  a typo in a request is a bug worth failing on, while an unexpected response
  field is a newer server. Do not send fields your target server does not know.

Event type codes are **permanent**. A code that has shipped is never reused for
a different meaning, because histories written years ago must still decode. This
is stronger than the protocol version guarantee — it holds across major versions
too.
